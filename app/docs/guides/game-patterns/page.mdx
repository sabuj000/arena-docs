# Model any type of game with Arena

Arena does not know the rules of your game. Your game server decides what happened, and the Arena API records it. This guide shows how to map four kinds of game onto the same few resources, so one integration approach works for a reaction game, a puzzle, a duel or a free-for-all.

## The standard round

Every pattern follows the same sequence. Your server makes these calls, in this order.

  rows={[

    { name: '2. Start the match', type: 'POST /v1/matches/{match_id}/start', desc: 'The match must be pending and have at least 2 players.' },

    { name: '4. End the match', type: 'POST /v1/matches/{match_id}/end', desc: 'Send results with a player_id and a placement for each player. The score is optional.' },
    { name: '5. Submit scores', type: 'POST /v1/leaderboards/{leaderboard_id}/scores', desc: 'Send the player_id and a score. Add the match_id to link the score to the match.' },
    { name: '6. Unlock achievements', type: 'POST /v1/players/{player_id}/achievements/{achievement_id}/unlock', desc: 'Unlocking is safe to repeat. If the player already has it, the request returns the original unlocked_at.' },
    { name: '7. Reward the player', type: 'POST /v1/players/{player_id}/inventory/grants', desc: 'Grant coins or other items. A grant adds an item with no payment.' },
  ]}
/>

For a full walk-through of steps 1 to 5 with requests and responses, see [Run a ranked match end to end](/docs/guides/ranked-match).

### Make the end of a round safe to retry

Steps 4 to 7 change data, and a network error can leave you unsure whether a call worked. Send an `Idempotency-Key` on each of them, and build the key from the match so a retry sends the same key.

```text
end-<match_id>
score-<match_id>-<player_id>-<leaderboard_id>
grant-<match_id>-<player_id>
```

This matters most for a leaderboard with `update_mode` set to `sum` and for grants, because repeating either one would add the points or the items twice. See [Handle errors and retries safely](/docs/guides/errors-and-retries).

## Design the leaderboards

Give each game its own leaderboards. Points from a reaction game and points from a word game are not comparable, so a shared leaderboard would rank one game against the other.

    { name: 'sum', type: 'update_mode', desc: 'Adds each new score to the player total. Use it for lifetime points or a count of wins.' },
    { name: 'latest', type: 'update_mode', desc: 'Keeps the newest score. Use it for a rating that your game recalculates after each match.' },

Players with equal scores share a rank, and the next rank is not skipped.

Choose leaderboard ids that name the game, for example `memory_weekly` and `memory_lifetime`. The id is a short key that you choose when you configure the leaderboard.

## Keep the game server in charge

Compute scores and results on your game server and send them from there with a secret key (`sk_`). A client that sends its own score can send any score. Publishable keys (`pk_`) are for reading leaderboards and achievements in a game client. See [Authentication](/docs/get-started/authentication).

## Checklist for a new game

- Decide the pattern from the table above, and write down how a round is scored.
- Create two leaderboards for the game: one for the best score and one for the total. Use ids that name the game.
- Decide who the second player is when one person plays alone.
- Build the idempotency keys for the end of a round from the match id.
- List the achievements that the game can award, and mark any surprise ones as hidden.
- Decide which items are rewards, which are consumables and which are entitlements.
- Test with the [sandbox](/docs/get-started/sandbox), including a declined payment and a retry after a failed request.
